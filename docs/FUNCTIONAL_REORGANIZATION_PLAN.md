# 功能整理与稳定性实施计划

2026-11-05更新。范围：先确保基础功能与AI可靠，再分模块整理功能。风格、配色、字体、圆角及大布局不执行，待另行讨论。全站视觉计划引用本文作为前置条件。

## 本轮已处理

### AI邀请错误

症状：网页显示已配置API，但生成时提示邀请无效。状态接口确认configured/ enabled均为true，有效期未到，不通过工具读取密钥文件。

代码缺陷：浏览器空邀请发出的“Bearer ”可能被HTTP裁剪成“Bearer”，旧解析只删除“Bearer ”前缀，残留非空字符串优先于有效Cookie。旧标签页的过期邀请也会覆盖本机会话；初始连接请求没有等待，存在建立会话与生成请求竞态。

修复：统一ai-client；生成/查询额度前等待本机连接检查；已配置时清除旧邀请且不发Authorization；服务端严格解析Bearer并优先使用有效本机Cookie；缺本机会话提示重新连接，停用/过期明确提示设置状态。不会自动重试收费生成。

### 业务数据一致性

AI面试建议增加稳定来源标识，相同建议重复采用不重复建轮次；岗位入账前再次检查来源去重。生成建议与实际动作继续分开，不能自动把“建议投递”变成“已投递”。

## 功能到底如何归属

| 数据/功能 | 唯一归属 | 对其他模块的关系 |
|---|---|---|
| 个人目标/时间/资格 | 个人画像 | 向机会筛选与AI提供上下文，不复制成多份画像 |
| 岗位事实/原文/来源 | 岗位快照 | 收藏、目标、申请均引用快照；目录更新不重写历史 |
| 学习任务/证据 | 目标岗位下的任务 | 资源、AI、手动都只是创建来源；完成状态只改同一任务 |
| 计划 | 任务的日期与顺序视图 | 不再另建一份能独立完成/变更的“计划任务” |
| AI建议 | 草稿/历史 | 采用后关联任务、轮次或岗位；建议自身不是事实 |
| 投递台账 | 一条求职申请 | 保留阶段历史、下一步和投递日期；不从链接点击推断 |
| 面试轮次/经验 | 申请下rounds | 独立时间线是聚合视图，不是第二份轮次数据 |
| Offer条件 | 申请下offer | 对比表读取同一数据；直接录入也创建Offer阶段申请 |
| 复盘 | 周期汇总+用户复盘 | 不重复维护当前进展和周复盘两个孤立统计 |
| AI连接/额度 | 本机服务 | 个人备份不带密钥；邀请只作为可选访问方式 |

## 按用户路线整理

### A 首次使用和选目标

1. 首次进入应询问方向、城市、求职类型、毕业时间和每周时间；未知允许留空。
2. 从目录收藏或手工录入一个岗位，查看来源，选择目标。
3. 缺目标时提供选目标入口，不用空仪表盘暗示已锁定。
4. 更换方向与更换具体岗位分开，明确影响范围。

验收：新用户无AI也能完成“画像→岗位→第一条任务”。切换目标不删除旧证据。待完成：将散落入口汇成明确引导，保持数据兼容。

### B 学习闭环

1. 手动、资源和AI三种方式创建统一任务。
2. 计划只回答何时做、先后顺序和容量；我的任务回答执行状态。
3. 完成必须有成果证据；暂停和重新安排不应丢失笔记。
4. 资源库展示可用入口、类型与适用范围；不能把选中资源算成完成。
5. 日历只记出勤足迹，任务统计只记完成；两个指标不混用。

待完成：统一state.tasks与backlog的ID、顺序和排期投影，避免在重排/编辑中跨数组移动造成重复；将AI计划与旧手动计划的历史统一为版本化元数据。需先做迁移与备份测试，不能直接删旧数组。

验收：采用一次只创建一次；每天至多3项、每周不超80%预算；0小时、无可用日、截止已过都可解释；改日期不改完成状态；旧备份可导入。

### C AI工作流

当前：四场景、只读上下文、固定prompt、一次模型调用、JSON/业务校验、本人采用、本地保存。不是自主多Agent或全网搜索。

先完善：

- 所有AI入口共用连接状态、错误展示、提交中状态；不再让设置、聊天、台账分别判断邀请。
- 上下文包含当前目标、有限任务、可用日、截止、资格、最近轮次，限制长度但不静默冒称完整读取全部历史。
- 目标变化或建议日期过期时要求重新核对，不把旧草稿套到新目标。
- AI输出可采用性在服务端检查，采用时再对当前状态复核，防止生成后用户已经改预算。
- 结果关联来源/生成时间；对话历史和计划历史按目标隔离，保存失败不能提示成功。
- 需要取消、持久错误或长回答等功能时单独增加业务测试，不直接上复杂Agent依赖。

真实联调门槛：目前仅真实对话链路用最小合成请求验证过。计划、投递与面试的结构化真实输出质量仍需少量联调；不能用对话成功代替全部AI验收。其他流程已用合成模型验证，后续联调不得展示或读取用户Key。

### D 投递和面试

1. 机会负责发现，投递建议负责排序，台账负责事实，边界清楚。
2. 每条建议给公司岗位、理由、行动、建议日期、来源和核验状态。
3. 加入台账先收藏，已投递由本人确认；重复来源进入已有记录。
4. 面试时间线聚合所有申请轮次，允许未来待安排、已安排、已完成和取消。
5. 经验与问题属于具体轮次，复盘可以引用它生成补缺任务。

待完成：将“建议准备节点”和“真实面试轮次”细分类型，避免项目复习也被当成真实面试；新增直接从现有申请进入AI面试规划的上下文范围。合并轮次编辑入口，不维护两份表单。

验收：阶段回退保留历史和Offer；同一AI轮次重复采用提示已有记录；完成日期与建议日期分别显示；建议不能自动改为面试或Offer。

### E Offer与复盘

1. Offer直接录入和阶段切换使用同一数据。
2. 对比只展示本人提供的条件，不猜薪资/年薪或判断录用结果。
3. 空白字段是待补充，缺失与0必须区分。
4. 复盘汇总真实事件，可从暴露问题创建下一条任务。

待完成：抽离统一Offer表单并实现选择2—4个对比；当前结构化表格可用但默认展示全部，后续控制比较范围。将两个复盘模块合并，旧备注转归档，不删内容。

### F 数据、启动和配置

固定本机地址，启动后检查实际服务版本；统一保存失败、跨标签冲突和备份导入预览。网页AI配置与高级邀请统一显示真实连接状态；密钥只由应用正常使用，助手不通过工具读取。

待完成：拆分应用状态与页面渲染，使错误可以在对应模块持续显示；避免只有3秒toast。完善“建议待保存/已保存/已采用”状态。迁移前先导出，导入失败必须保留现有库。
