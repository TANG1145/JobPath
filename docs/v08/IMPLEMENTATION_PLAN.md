# JobPath v0.8 重构实施方案

**版本目标**

让用户围绕一个真实目标岗位，完成“理解要求—识别差距—复用成果—针对性准备—记录投递”的连续流程，并在每次打开应用时知道下一步做什么。

本版采用渐进重构。保留已有规则、排程、配额、数据保护和测试，不同时重写所有模块。

本方案取代初始文档中的部分功能与交互设计。原有 60 人时、100 元等约束不自动视为本次重构的已确认预算；实施前根据阶段任务重新估算，若资源不足，优先延后新增 AI 能力。

**一、新的功能范围**

| 类别 | v0.8 范围 | 完成定义 |
|---|---|---|
| 今日工作台 | 截止事项、今日重点、继续上次任务或练习 | 首屏存在明确可执行动作；无数据时提供开始入口 |
| 目标岗位 | 导入 JD、收藏、要求确认、优先级、岗位工作区 | 每个岗位可集中查看要求、准备、材料和投递 |
| 差距诊断 | 区分缺能力、缺证据、缺表达、已有可用材料 | 每项差距都能进入合适动作，而非一律生成学习任务 |
| 学习计划 | 共性任务、容量限制、已有能力验证、重排预览 | 多岗位共享任务；完成记录不因切换目标或重排消失 |
| 成果库 | 独立成果记录、验证说明、多岗位关联 | 同一成果可以复用于不同岗位、材料和练习 |
| 投递管理 | 列表筛选、下一步、轮次、时间线、材料版本 | 能回答“何时投了什么材料，接下来做什么” |
| 练习 | 一次一题、回答版本、历史反馈、再次练习 | 练习结果可回看，不能只保存在一次弹窗中 |
| AI 增强 | JD 提取、基于事实的表达建议、针对性文字反馈与有限追问 | 输出有上下文、有来源、可确认、可拒绝、可降级 |
| 数据保护 | 旧备份迁移、导出恢复、冲突检测、保存反馈 | 不以迁移为由清空或静默覆盖用户数据 |

**合并或降级的功能**

- 两套资源入口合并为一个目录，主要通过任务详情访问。
- 两套复盘合并为“行动回顾”，结果可转为待确认任务。
- 固定五题保留为可选模板，不继续扩建独立题库。
- 公开岗位目录定位为精选参考，不以固定数量作为版本成功标准。
- Offer 对比仅在相关阶段出现；旧备注进入历史资料。
- 4/8 周路线作为折叠概览，日常主视图只显示近期可执行任务。
- 原始匹配总分从主界面移除，优先展示已知要求、证据与待确认事项。

**本版不做**

账号与跨设备自动同步、全网抓取、自动投递、邮件接入、音视频面试、在线代码执行、完整简历排版器、微服务和向量数据库。

这些是后续候选，不是永久禁止项。加入时需明确用户价值与维护成本。

**二、页面与核心交互**

主导航改为“今日、目标岗位、成长与作品、练习”，设置进入辅助菜单。

| 页面 | 核心内容 | 主要操作 |
|---|---|---|
| `/today` | 最近截止、今日重点、继续上次活动、备份提示 | 开始任务、准备面试、记录行动 |
| `/jobs` | 我的岗位、阶段/优先级筛选、精选示例 | 导入 JD、打开岗位、调整优先级 |
| `/jobs/:id` | 岗位工作区 | 查看要求、关联成果、准备材料、记录投递 |
| `/growth` | 跨岗位共性差距、近期任务、成果库 | 生成计划、验证能力、创建成果 |
| `/growth/tasks/:id` | 单个任务详情 | 开始、修改估时、提交成果、暂缓 |
| `/growth/evidence/:id` | 成果与使用记录 | 编辑事实、关联岗位、生成表达草稿 |
| `/practice` | 待练习项、模板、历史会话 | 新建练习、继续练习、查看反馈 |
| `/practice/:id` | 题目、回答、反馈和历史版本 | 保存回答、请求反馈、再次练习 |
| `/settings` | 画像、时间、AI 配置、备份与隐私 | 修改偏好、恢复数据、查看存储状态 |

路由必须支持刷新、前进后退和直达。筛选条件进入 URL，临时输入进入草稿，不把个人正文写入 URL。

**首次进入**

提供两个入口：

1. “我已有目标岗位”：粘贴 JD，先保存，再补充信息。
2. “我还在探索”：浏览方向和示例，选择后再补画像。

未填写时间和方向时保持“未设置”，不把默认值表述为用户选择。完整画像不作为开始使用的前置条件。

**岗位导入与要求确认**

采用“输入—整理—确认”三步：

- 输入：粘贴 JD，职位和公司允许后补；来源链接可选。
- 整理：手动整理或请求 AI；原文始终保留。
- 确认：逐项检查必需/优先、技能关系、原文依据和待核实项。

桌面使用原文与结构化要求双栏；移动端切换“原文 / 要求”，保留编辑位置。用户可以逐项接受、修改或删除 AI 建议。

导入完成后进入岗位工作区，主操作为“看看我还需要准备什么”。

**岗位工作区**

使用四个子页签：

- **概览**：岗位状态、优先级、截止事项、下一步。
- **要求与准备**：要求依据、差距类型、关联任务和成果。
- **材料与练习**：项目表达、投递材料版本、相关练习。
- **投递记录**：阶段、实际日期、轮次、历史与 Offer 信息。

保留一个“当前重点岗位”，但其他岗位仍可同时准备。切换重点只影响首页排序，不删除、归档或重置其他岗位的数据。

**今日工作台**

默认最多突出三项重点，排序规则可解释：

1. 已到期或近期的面试、笔试、申请事项；
2. 用户手动置顶；
3. 当前重点岗位的阻塞任务；
4. 其余近期任务。

用户可以改排序或暂缓。没有明确截止日期时不制造紧迫感。

**任务与成果**

任务详情展示：

- 为什么要做，服务哪些岗位要求；
- 预计时间、先修条件；
- 一个主资源和按需展开的备选；
- 验收要求；
- 已有关联成果。

完成任务时允许“创建成果”或“关联已有成果”。行政类行动，例如确认面试时间，不强制填写实践证明。

调整任务估时后重新计算容量；超出预算时提示重排或移入待办，不静默保留虚假的容量数字。

**练习**

用户从岗位、成果或模板发起练习：

选择范围 → 一次一题 → 保存回答 → 查看反馈 → 修改后再练或生成补缺任务。

反馈区固定展示：

- 引用的回答片段；
- 已覆盖内容；
- 未回答或证据不足的部分；
- 可执行的改进建议；
- 可选追问。

反馈不会自动修改成果事实或技能等级。关闭页面、刷新或切换岗位后，已保存的练习仍可恢复。

**通用交互标准**

- 主要表单附近显示“未保存 / 保存中 / 已保存 / 保存失败”。
- 复杂编辑使用完整页面或宽侧栏，小型编辑使用短弹窗。
- 可逆操作优先提供撤销；外发数据、覆盖导入和删除保留明确确认。
- AI 入口就地显示可用状态、额度及本次发送内容。
- 首屏弱化装饰仪表，保留复古配色与品牌元素。
- 正文与输入区以 14—16px 为基准；状态不能只依赖颜色。
- 键盘焦点可见，弹窗关闭后返回触发位置。

**三、数据模型**

核心原则：岗位、要求、任务、成果、材料和练习分别保存，通过稳定 ID 关联。不要继续把所有业务数据作为一个大对象反复整体写入。

| 实体 | 关键字段 | 作用 |
|---|---|---|
| `Profile` | `id`、求职偏好、时间预算、时区、技能自评、`revision` | 未知能力与零基础分开 |
| `Job` | `id`、公司、职位、方向、优先级、`activeSnapshotId`、归档状态 | 用户长期管理的岗位对象 |
| `JobSnapshot` | `id`、`jobId`、版本、原文、来源、核验状态、创建时间 | 保留不同时间的岗位事实 |
| `Requirement` | `id`、`snapshotId`、类别、技能、all/any、原文引用、确认状态 | 岗位要求的可追溯表达 |
| `Task` | `id`、类型、状态、日期、估时、先修、验收项、`revision` | 支持学习、验证、表达和求职行动 |
| `TaskRequirement` | `taskId`、`requirementId` | 一个任务服务多个岗位要求 |
| `Evidence` | `id`、标题、个人贡献、验证说明、结果、链接、证明类型 | 可复用成果事实 |
| `EvidenceLink` | `evidenceId`、`requirementId`、适用说明 | 明确成果如何支持要求 |
| `TaskEvidence` | `taskId`、`evidenceId` | 完成任务与已有成果之间的关系 |
| `Plan` | `id`、周期、容量、岗位范围、版本、状态 | 计划配置与历史 |
| `PlanItem` | `planId`、`taskId`、安排日期、估时快照 | 重排不复制或丢失任务身份 |
| `Application` | `id`、`jobId`、`snapshotId`、阶段、下一步、实际投递日期 | 绑定当时的岗位快照 |
| `InterviewRound` | `id`、`applicationId`、名称、日期、状态、记录 | 独立保存轮次 |
| `MaterialVersion` | `id`、用途、正文、关联成果、版本、确认状态 | 简历片段或项目表达版本 |
| `ApplicationMaterial` | `applicationId`、`materialVersionId`、使用时间 | 回看实际使用的材料 |
| `PracticeSession` | `id`、岗位/成果关联、上下文快照、状态 | 一次可恢复的练习 |
| `PracticeTurn` | `id`、会话、题目正文、题目来源、顺序 | 不再只保存 q1 等无语义编号 |
| `AnswerVersion` | `id`、`turnId`、正文、版本、时间 | 修改回答不覆盖旧回答 |
| `Feedback` | `id`、`answerVersionId`、内容、生成信息、采纳状态 | 反馈绑定具体回答版本 |
| `Draft` | 编辑对象、正文、基础版本、更新时间 | 草稿与正式状态隔离 |
| `Event` | 对象、事件类型、时间、必要元数据 | 支撑时间线和复盘 |

可修改实体统一包含 `createdAt`、`updatedAt`、`revision`；事实快照和历史版本尽量采用追加保存。

**关系与不变量**

- 一个岗位有多个事实快照，申请绑定实际使用的快照。
- 一项任务可服务多个要求，一份成果也可支持多个要求。
- 一个回答版本可以对应多次反馈，但必须显示时间与来源。
- 修改回答后，旧反馈标记为“针对旧版本”，不能混作当前结论。
- 取消关联不删除成果本体。
- 任务完成不自动提升技能等级，也不自动改变投递阶段。
- 公共目录更新不自动覆盖私人岗位。
- AI 建议与用户确认事实分开保存。

**存储与一致性**

继续使用 IndexedDB，引入薄访问层和共享校验 Schema：

- 单对象编辑使用 revision 检查；
- 跨对象操作在同一事务中完成；
- 其他标签页的更新可通知当前页面，但通知不代替事务校验；
- 输入先暂存草稿，正式保存只更新相关记录；
- 保存失败保留输入并提供恢复入口。

**旧数据迁移**

采用可重复执行的版本迁移：

1. 读取旧数据并完整验证。
2. 保存旧格式恢复副本。
3. 在内存中生成迁移预览和数量统计。
4. 将旧岗位转为 `Job + JobSnapshot`。
5. 将任务证据转为成果记录，标记为旧版迁移、自报证明。
6. 旧回答保留为旧版练习；没有题目或上下文的历史不得补造。
7. 旧 Offer 备注作为历史记录保留，不自动猜测其所属申请。
8. 生成新存储并核对数量与引用。
9. 成功后切换读取版本，保留恢复入口。

存在歧义的历史记录进入“待整理”，不得自动合并或静默丢弃。迁移失败继续保留旧数据，不调用清空数据库作为修复措施。

**四、差距与计划规则调整**

差距诊断采用以下四种动作类型：

| 状态 | 判断依据 | 推荐动作 |
|---|---|---|
| 待确认 | 原文不明确、自评未知或材料不足 | 核实要求或做小型验证 |
| 缺能力 | 用户明确不会，或验证暴露具体缺口 | 学习与实践 |
| 缺证据 | 用户认为会，但暂无适用成果 | 验证任务或补充成果 |
| 缺表达 | 已有关联成果，但材料未清楚覆盖要求 | 整理表达、针对性练习 |
| 可复用 | 已有用户确认的适用成果与材料 | 用于投递，按需复习 |

这些状态是准备建议，不是能力认证或招聘资格判定。

计划生成顺序：

1. 读取所选岗位的已确认要求。
2. 合并共性技能和重复任务。
3. 检查已有成果及用户确认的能力。
4. 已掌握部分提供验证或跳过选项。
5. 补充必要先修。
6. 按优先级、截止和容量排入近期计划。
7. 展示新增、移动、暂缓和未排入项。
8. 用户确认后写入。

自评满级不等于自动免除所有验证，也不应强制重复整套基础课程。

**五、框架与迁移顺序**

目标前端采用 React、TypeScript、Vite，使用共享运行时 Schema 校验外部输入。状态先使用组件状态与轻量领域服务，出现明确需要再增加状态库。

保留现有 Node/SQLite 网关，抽出供应商适配和配额接口。是否迁移 Workers/D1，在部署阶段单独决定。

建议目录：

```text
src/
  app/          路由、导航、应用壳
  features/     岗位、任务、成果、投递、练习
  components/   表单、弹窗、状态与通用组件
  domain/       差距、排程、状态转换
  storage/      仓储、事务、迁移、备份
shared/
  schemas/      数据与 API 契约
  types/
server/
  ai/           场景编排、供应商适配
  quota/
tests/
  unit/
  contract/
  e2e/
  migration/
```

迁移顺序固定为：

1. 固定旧版行为、测试和数据夹具。
2. 定义新模型、Schema 和迁移规则。
3. 建立 React 应用壳、路由和通用表单。
4. 迁移设置与存储状态，验证读写边界。
5. 迁移目标岗位与岗位编辑。
6. 迁移任务、成果及计划。
7. 迁移申请、材料与练习。
8. 接入新的 AI 场景。
9. 删除已无引用的旧渲染与重复逻辑。

过渡期只允许一个正式数据写入入口。未迁移页面通过适配层访问同一仓储，避免两套状态分别保存。

现有测试框架可以暂时保留，无须为了技术栈统一同时重写全部测试。

**六、AI 契约与交互边界**

AI 场景按业务意图区分，避免一个自由聊天接口承担所有功能：

| 场景 | 必要输入 | 输出 |
|---|---|---|
| JD 整理 | JD 原文、允许的结构化字段 | 要求草稿、原文引用、未知项、待核实问题 |
| 项目表达 | 用户选择的成果事实、岗位要求、表达用途 | 草稿、事实引用、缺失信息 |
| 回答反馈 | 题目正文、评价维度、答案版本、经同意的岗位/成果摘要 | 引用式反馈、改进建议、可选追问 |

请求应记录上下文版本、场景版本、幂等键；反馈保存模型及生成时间等来源信息。服务端不接受任意 system prompt 或任意上游地址。

客户端流程：

准备输入 → 预览发送内容与额度 → 用户确认 → 请求中 → 成功/失败 → 审阅结果 → 保存或转成待确认行动。

切换页面后应能找回已返回的结果。取消等待不等于取消计费，界面应如实表达。

新练习采用“有限轮次的会话预算”。具体轮次与额度以最大输入测试和真实计费校准决定，不直接沿用每天两次调用，也不承诺无限追问。

**七、分阶段验收**

| 阶段 | 交付内容 | 必须通过的验收 |
|---|---|---|
| A：基线与范围冻结 | 页面清单、模型说明、旧数据夹具、AI 契约草案 | 现有测试可复跑；主要流程与已知缺陷有记录；新旧数据映射无未决的破坏性处理 |
| B：数据层与迁移 | 新 Schema、仓储、迁移和恢复 | 旧数据数量及关键正文保留；引用有效；重复迁移不重复创建；失败不破坏原数据；双标签冲突不静默覆盖 |
| C：前端壳与岗位工作区 | 新导航、路由、岗位导入和详情 | 刷新/前进后退/直达正常；手动 JD 完整可用；原文与要求可对照；首次使用不制造虚假目标状态 |
| D：任务、成果与今日页 | 差距分类、共性任务、成果复用、容量重排 | 一份成果可关联两个岗位；同一共性任务不重复安排；满级自评不强制重学；调整估时后容量正确；历史证据保留 |
| E：投递、材料与非 AI 练习 | 申请时间线、材料版本、回答历史 | 能回看投递所用版本；回答修改保留历史；旧反馈明确标为旧版本；AI 关闭仍可记录和练习 |
| F：AI 场景接入 | 三类场景及质量评估 | 上下文完整、输出校验、结果可回看；超时/坏 JSON/重复提交/耗尽均不破坏本地状态；未确认输出不写入事实 |
| G：用户验证与发布准备 | 可用性记录、性能与恢复检查、部署决策 | 核心用户任务通过；阻断问题清零；真实 AI 和公网分别验收，未验证能力明确标注 |

**补充验收样例**

- **迁移**：覆盖空数据、普通旧备份、历史计划、旧 Offer 备注、重复 ID、未来版本、损坏引用、迁移中断与重试。
- **计划**：覆盖零时间、一天可用、跨周先修、多岗位共性任务、已有成果、过期截止、取消重排、已完成任务占用。
- **AI**：固定不少于 20 个代表性样本，覆盖正常输入、缺上下文、矛盾事实、虚构指标诱导、无关回答和要求歧义。格式通过与内容质量分别记录。
- **交互**：在 390px、768px、1280px 下走完关键流程；主操作可键盘触达，错误可发现，刷新不丢已保存内容。
- **性能**：用含 50 个岗位、500 项任务、200 份成果的合成数据检查列表和编辑体验；记录测试设备，不把单机结果当成所有设备保证。

**用户任务验收**

邀请至少五位目标用户，分别完成：

1. 导入自己的目标岗位并确认要求；
2. 判断一项差距属于哪种问题；
3. 关联或创建一份成果；
4. 完成一次练习并找到改进建议；
5. 设置一个下一步求职动作。

建议门槛：至少四位无需主持人代操作完成核心流程；记录用时、卡点和误解，不以“觉得好看”替代任务成功。

首次岗位导入到第一项有用动作，目标控制在十分钟内。该数值是版本验证目标，不是当前已达到的结论。

**发布阻断条件**

任何数据丢失、静默覆盖、迁移不可恢复、未确认外发、重复收费请求、AI 虚构内容被自动写成事实、核心流程无法完成，都阻断发布。

外观细节、次要筛选和高级视图可以后置，但必须列入已知问题。

**八、开发任务拆分原则**

每个任务只覆盖一个可独立验收的行为，例如“把同一成果关联到两个岗位”，而不是“完成全部成长模块”。

每个任务单必须包含：

- 用户触发场景与预期结果；
- 输入输出与数据变化；
- 允许修改的模块；
- 失败、取消、刷新和冲突行为；
- 自动验证与必要人工检查；
- 对旧数据和旧功能的影响；
- 回退方式。

建议设置两个交付点：

- **v0.8 基础版**：完成 A—E，核心闭环不依赖 AI。
- **v0.8 AI 增强版**：完成 F—G，在同一结构上增加经过验证的智能辅助。

这样即使真实模型质量、计费或部署验证延期，产品重构本身仍能形成完整、可使用的交付。
